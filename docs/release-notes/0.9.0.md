# Looper 0.9.0

Looper can recover blocked runs from proven orchestration defects. The
controller asks the review agent for a structured proposal, applies permitted
changes after active work drains, and retries retained implementation work.
Repair attempts and effective command corrections survive restart. Recovery
events distinguish application, integration, successor dispatch, and blocked
retries. External prerequisites remain blocked.

- Verification failures identify added, modified, and deleted paths. Full path
  comparisons stay beside check logs. Snapshot errors retain their cause.
- Bootstrap rejects private source paths and permits one corrected response.
- Stable finding keys prevent renamed prerequisites from creating duplicate
  tasks. Operator ownership keeps human actions outside the worker queue.
  Duplicate evidence preserves completed status and active task contracts.
- Status reports executable and controller builds when they differ.
- Installation defaults to Looper-specific skills. Generic workflow skills are
  optional. Bootstrap source validation supports custom backlog names.

The combined recovery fixture preserves T001 implementation work, corrects its
contracts, repairs an unignored cache, integrates T001, and dispatches T002.
It also covers restart after repair application. The test suite uses local
agent fixtures. No paid agent calls or external credentials are required.

Validation: `make test` passes, including all 55 runtime fixtures, static
analysis, installer tests, build checks, packaging, and skill checks. Focused
race tests pass. The dispatch fixture uses a start barrier instead of a fixed
sleep to check overlapping work.

Installation updates future controller runs. Existing controllers keep their
original executable until restart. Unknown sources and administrative tasks
without the required evidence remain blocked.
