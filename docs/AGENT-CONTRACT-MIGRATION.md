# Migrating Looper machine contracts

Date: 2026-11-05. Owner: AX-001 in `docs/AGENT-EXPERIENCE-PLAN.md`.

This guide explains how Looper moves from today's machine output (contract
version 1, `legacy`) to the bounded version 2 documents defined in
`docs/AGENT-CONTRACTS.md`, and what a caller must do. It resolves the
compatibility promise in `docs/UI-PLAN.md` — "existing `--json` workflows
keep byte-compatible output" — through an explicit version selection and a
documented default transition. Looper never changes a legacy shape silently.

## What stays unchanged

- Every command that today prints JSON keeps printing the same JSON, byte for
  byte, for the same saved run, unless the caller selects version 2.
- Exit codes 0, 1, and 2 keep their current meanings. New codes appear only
  for calls that select version 2 or use new commands.
- The NDJSON event stream keeps its line format. `--follow` keeps streaming
  NDJSON under both versions.
- The task file schema `to-do.schema.json`, the profile, controller metadata,
  view snapshots, and the request and acknowledgement files keep their
  version 1 documents.

## Opting in to version 2

Version selection is valid for every command: under version 2 every failure
returns the structured error document (`looper.error`) with the transport
exit codes below. Success documents still ship per command as their owning
tasks land; a command whose version 2 success document has not shipped keeps
its legacy success document, detectable by the missing `contract_version`
field. Today `version`, a finite `events` query, `status`, `recovery
--preview`, `inspect`, `preflight`, `runs`, `requests`, `wait`, and `doctor`
serve their version 2 success documents.

Per invocation:

```bash
looper status --contract v2 --json
looper events --contract v2 --after 1200 --json
looper add-plan docs/PLAN.md --contract v2 --json --idempotency-key import-3
```

For a whole session or script:

```bash
export LOOPER_CONTRACT=v2
```

Precedence: the `--contract` flag wins over `LOOPER_CONTRACT`; an unset
environment variable selects the default version. An unsupported value is a
usage error (exit 2) with the supported range in the message.

## Caller migration steps

1. Pin the contract version explicitly. A script that parses JSON should pass
   `--contract v2` or set `LOOPER_CONTRACT=v2` so a later default change
   cannot surprise it.
2. Replace whole-state parsing with the compact fields you need. `status
   --contract v2` answers identity, ownership, active work, waiting reason,
   request counts, last transition, and cursor without the complete backlog.
   Add `--full` where you truly need everything.
3. Replace event polling with pages and finite waits:
   - `looper events --contract v2 --task T015 --limit 50` returns one page
     with `items`, `page.high_water`, `page.has_more`, and a `continuation`
     command.
   - `looper inspect T015 --contract v2 --json` returns one bounded task
     view: the contract, blockers, the current attempt, the newest checks,
     and the routes that page the attempt (`--after`) and check
     (`--checks-after`) history without duplication or gaps.
   - `looper wait --contract v2 --cursor 1202 --timeout 30s` returns one
     outcome document instead of a polling loop.
4. Replace acknowledgement parsing with receipts and records:
   - A mutation returns `looper.request.receipt` immediately. Its `request.id`
     is durable.
   - `looper requests <id> --contract v2` returns `looper.request.record`
     with the lifecycle state from `docs/contracts/request-states.json`.
   - A wait timeout leaves the request running. Retry the wait or query the
     record; do not resubmit unless you want a second request.
   - `looper stop --wait --contract v2` replaces a stop-and-poll loop with
     one bounded wait for the durable drain result, bound to the stopped
     controller's session: `applied` when that controller drained, `rejected`
     when it exited before honoring the request or a replacement controller
     swept it. The wait decides nothing itself and never stops a newer
     controller.
   - Make retries idempotent with a caller key: pass `--idempotency-key <k>`
     on `add-task`, `add-plan`, `cancel`, `amend`, and `config` (1-128 bytes, no
     control characters). The same key and payload returns the original request —
     the immediate receipt carries `duplicate: true`, and a `--wait` whose
     original already decided reports its record — while a changed payload
     under the same key returns the `idempotency_key_conflict` refusal.
     Distinct keys with identical content both apply. A key answers from the
     retained request receipts: undecided requests always keep theirs and at
     most the newest 200 decided receipts stay per run, so a key whose
     receipt was pruned behaves as fresh.
5. Stop parsing human text. Failures you must handle programmatically return
   `looper.error` documents with a stable `code`, `retry` guidance, and
   `next_actions`. This is live for every command under version 2 (AX-014):
   a JSON caller reads exactly one document from standard output whether the
   call succeeded or failed, and the `retry` field distinguishes a retryable
   wait (`yes`), changed input (`after-change` with `expected` and `observed`
   values), and a refusal (`no`). `unknown_evidence` names the evidence a
   recovery recommendation would need, so an unsupported recovery never looks
   like an unavailable one.
6. Check capabilities before submitting to an older controller. Read
   `looper version --contract v2 --json`: its `controller` section reports the
   live controller's session, build, contract versions, and request types.
   Submit only request types that section lists.

## Controller capabilities and older controllers

`runtime/controller.json` carries a `capabilities` record from AX-008 on. It
lists the contract versions and public request types the live controller
accepts, plus the limits it enforces today. Controllers built before AX-008
write no record. The policy for both cases:

- **Record present.** A client validates the request type against
  `capabilities.request_types` before publishing an envelope. A type the
  controller does not list is refused locally, with the session and the
  supported list in the message, and nothing is queued. The controller
  validates again when it claims: an envelope of a type it never claims
  receives an `error` acknowledgement naming the type, the supported list,
  and this document, and the envelope is removed rather than left waiting.
- **Record absent.** The controller predates the capabilities contract. The
  compatibility set is `add-task`, `add-plan`, `settings`, `requeue`, and
  `stop`: every controller since the accepted baseline accepts these. A
  client may submit them; the capabilities document reports the derivation
  with `absent_metadata: true`. Any other type — `cancel-task` (advertised
  by controllers since AX-019 but not part of the frozen base set),
  `amend-task` (advertised since AX-020, same status),
  `recovery` (advertised since AX-017) — is
  refused before publication, because an older controller could only leave
  it as a dead letter.
- **Stale sessions.** Session-bound requests (`add-task`, `settings`,
  `requeue`, `cancel-task`, `amend-task`, `recovery`) name the controller session they target. If that session no
  longer owns the repository, publication is refused, or a wait in progress
  reports the change: which session the request targeted, which owns the
  repository now, and that resubmitting against the current controller is
  the next step. Plan imports are exempt: their receipts survive restarts
  and the next controller replays them.
- **Stop requests.** The stop transport is the scoped stop file, not a
  request envelope. `stop` is part of the advertised set, and `looper stop`
  refuses before writing the file when a live controller advertises a set
  without it.

Exit codes do not change in this step: a capability refusal is a refusal to
act, which lands in exit code 1 until the version 2 transport codes ship.

## Default transition

The default contract version stays `legacy` until all of the following hold:

1. The stage 1 to 4 deliveries in `docs/AGENT-EXPERIENCE-PLAN.md` are
   complete, and AX-026 documents every command.
2. AX-027 measures the public workflows against the audit fixtures and the
   release gates in the plan pass.
3. The release notes for the release that flips the default name the change,
   the new default, and the one-line opt-out (`--contract legacy`).

Flipping the default is a release decision, not a code cleanup. When it
happens, append the release name to `legacy_default_until` in the
capabilities fixture and add a dated entry to the change log below.

## Legacy invocations

Old spellings and workflows keep working where they ever did. This table names
each one, what replaces it, and which behavior actually changed. Only the last
row changes what an old invocation did.

| Legacy invocation | Current form | Notes |
| --- | --- | --- |

| `looper status --json` | `looper status --contract v2 --json` | Unchanged and byte-identical. The compact document is the bounded default under version 2; `--full` keeps the complete state. |
| `looper events --json` (drains the whole journal) | `looper events --contract v2 --json` | The legacy drain is unchanged. The version 2 call returns one bounded page with a continuation command; `--full` keeps the complete export. |
| Polling `status` or `events` in a loop | `looper wait --contract v2 --request <id> --timeout 30s --json` | One bounded call replaces the loop. Exit 5 is the timeout outcome, not a failure. |
| `looper add-task f.json --json` blocking up to 30 s for the acknowledgement | `looper add-task f.json --json` | The same invocation now returns the immediate receipt. Pass `--wait` for exactly the acknowledgement the default printed before. |
| `looper add-plan p.md --json` blocking up to 60 s | `looper add-plan p.md --json` | Same change: the receipt returns at once; `--wait` restores the applied acknowledgement, bounded by `--wait-timeout`. |
| Reading `runtime/acks/` or `state.db` for an outcome | `looper requests <id> --contract v2 --json` | The durable receipts are the public record; the acknowledgement files are swept transport. |
| Editing `to-do.json` mid-run to change or withdraw work | `looper amend <task-id> <task.json>`, `looper cancel <task-id>` | Checked requests replace the unsupported edit; the file edit still imports at a boundary when it replays, and the recovery preview explains a refusal. |
| `looper bogus-command`, `looper help` (parsed as a task file, printed a launch line, then failed on a guard) | usage error, exit 2 | Changed by AX-026: a bare word that names no command and no file is refused before anything starts. ## Changing a contract shape

Anyone changing a machine document follows one sequence:

1. Change the code.
2. Update the schema in `docs/contracts/schemas/`.
3. Record the new structure: `go test ./internal/looper -run
   TestLegacyContract -update-contract-fixtures`.
4. Add a dated entry to the change log below, naming the document, the
   change, the version it ships in, and the caller impact.
5. Run `go test ./...` and `make test`.

For legacy documents, the only permitted changes are the ones this guide
names: a legacy shape may gain a new optional field only when the field is
required by a controller feature that cannot wait for the default transition,
and only together with a change-log entry and a schema update. Anything else —
renaming, removing, retyping, or making an optional field required — ships in
version 2 only.

The guard is executable: `TestLegacyContractShapesAreFrozen` in
`internal/looper/compatibility_test.go` fails on any structural difference
from the recorded fixtures, `TestLegacyContractBytesAreFrozen` in
`internal/looper/legacy_bytes_test.go` fails on any byte difference — a
formatting-only change included, because it records full example documents
with fixed times, identifiers, and build identity and compares the live
output byte for byte — and `TestVersionTwoFixturesMatchSchemas` in
`internal/contractschema` fails when a version 2 fixture and schema disagree.
